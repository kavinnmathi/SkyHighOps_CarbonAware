# Datasets

Three data origins appear in this project and every output labels which one it uses.

| Label | Meaning |
|---|---|
| `REAL_OBSERVATION` | read from a real public dataset |
| `SYNTHETIC_SAMPLE` | generated by this project's seeded generator; **not real** |
| `SIMULATED_ASSUMPTION` | a value the real data does not contain (e.g. node latency, power draw) |

## 1. Default (included): synthetic sample data
Files in `data/sample/` were produced by `src/data_sources.py` (`generate_synthetic_carbon`, `generate_synthetic_workload`) with fixed seeds. They have a daily + weekly pattern plus slow noise for carbon intensity, and random jobs with CPU, memory, latency and delay-tolerance attributes. They exist so the project runs offline with nothing to register for. **Do not present results from them as real-world findings.**
If you delete them, the program re-creates them.

## 2a. Real carbon intensity: NESO historic generation mix CSV (preferred, via `import-carbon`)
- Source: NESO Data Portal, "Historic generation mix and carbon intensity" (`df_fuel_ckan.csv`), URL in `src/carbon_import.py` (the `utm_source=chatgpt.com` tracking suffix was removed).
- Half-hourly GB data; the importer reads only `DATETIME` and `CARBON_INTENSITY` (gCO2/kWh), keeps the newest N days, and treats values <= 0 or > 1500 as gaps (the loader interpolates up to 6 steps).
- `CARBON_INTENSITY` is NESO's estimate of actual intensity from the generation mix; it is used as the observed series. Timestamps are parsed as UTC (assumption).
- It is a periodically updated file, not a live stream: check `data_age_hours` in the provenance JSON.
- Provenance labels: `REAL_OBSERVATION`, `CACHED_REAL_OBSERVATION` (offline re-use of an earlier real import), `SYNTHETIC_FALLBACK` (not real).

## 2. Real carbon intensity: UK National Grid Carbon Intensity API (optional)
- Source: https://api.carbonintensity.org.uk/ (open, no API key needed).
- Half-hourly national GB carbon intensity with `forecast`, `actual` and `index` fields, in gCO2/kWh. History is available back to 2017, and each request may span at most 14 days, so the downloader uses 13-day chunks.
- Download: `python main.py download-carbon --start 2026-07-01 --end 2026-08-15` writes `data/real/carbon_intensity_gb.csv` with columns `from, to, forecast, actual, index, data_origin`.
- Preprocessing: the `actual` column is used; where it is missing the `forecast` column fills in. Gaps of up to 6 half-hours are interpolated, longer gaps raise an error. The loader reports how many points were filled.
- Check the API's own terms before redistributing the data.
- Minimum length: 7 days training + simulation days + drain steps (default 16 days). 30 to 60 days is better.

**Why per-site carbon intensity is simulated:** the project uses the GB national series for all sites, then derives each site's series as `ci_scale x base(t + ci_shift_steps)` (see `config/default_config.json`). That is a **simulated assumption** to create spatial differences between sites. It is not real data for other regions.

## 3. Real workload: Google Cluster Data 2019 (optional, manual)
- Source: https://github.com/google/cluster-data (version 3 / ClusterData2019: eight Borg cells, May 2019, CC-BY licence).
- The 2019 trace is about 2.4 TiB compressed and is distributed **only via Google BigQuery**, so it needs a Google Cloud account. That is why it is optional.
- A starter query is in `docs/google_trace_bigquery.sql`. It aggregates `instance_usage` rows per instance (first start, last end, average CPU and memory usage). Before running it, **check the table path and column names against the official trace documentation** ("Google cluster-usage traces v3"), and check the bytes-processed estimate that BigQuery shows before you run it.
- Export the (small, LIMITed) result as CSV to `data/real/google_trace_extract.csv`. Required columns: `collection_id, instance_index, start_time, end_time, avg_cpus, avg_memory`. Times are microseconds as in the trace; CPU and memory are in the trace's normalised units.
- Mapping (`load_google_trace_extract`):
  - REAL: arrival time, duration, average CPU and memory usage (rescaled by `google_trace_mapping.cpu_scale_cores` and `mem_scale_gb` in the config; this rescaling is an assumption).
  - SIMULATED: `cpu_util`, latency requirement, delay tolerance (slack) and migration data size, drawn with a seeded RNG, because the extract does not contain them.
- Run: `python main.py run --mode real`. If `data/real/google_trace_extract.csv` is absent, real mode uses real carbon data with the synthetic workload and says so in the console and report.

## 4. Other sources considered, not used
- Google Cluster Data 2011 (single 12.5k-machine cell): simpler to obtain but older than the paper's 2019 trace.
- Regional UK carbon-intensity endpoints: not used so that the project depends only on the national endpoint that was verified.
